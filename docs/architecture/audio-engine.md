# Аудиодвижок

Крейт `vyra-audio` не зависит от Tauri, SQLite и остальных крейтов VYRA, кроме общих типов. На вход он получает команды и источники звука, наружу отдаёт события. Об альбомах, очереди и профилях он не знает.

## Конвейер

```
          команды                                   события
 ядро ──────────────►  управляющий поток  ──────────────────►  ядро
                              │
        ┌─────────────────────┼───────────────────────┐
        ▼                     ▼                       ▼
  поток декодера  ──►  поток обработки  ──►  кольцевой буфер  ──►  поток вывода
  чтение файла         ресемплинг, DSP,       около 150 мс         WASAPI по событию
  и декодирование      громкость, дизеринг                         MMCSS «Pro Audio»
        │
  буфер PCM 2–4 с
```

Между декодером и обработкой стоит большой буфер. Он сглаживает паузы диска и сети. Между обработкой и выводом буфер маленький, поэтому движение ползунка эквалайзера слышно примерно через 150 мс.

Поток вывода работает по жёстким правилам: никаких блокировок, выделений памяти и записи в лог. Он забирает готовые байты из кольцевого буфера без блокировок (`rtrb`) и передаёт их в WASAPI. Если данных не хватило, поток выводит тишину и увеличивает атомарный счётчик; о пропуске сообщает управляющий поток.

Приоритеты потоков: вывод зарегистрирован в MMCSS как «Pro Audio», обработка идёт с повышенным приоритетом, декодер с обычным. Потоки сканера медиатеки работают в фоновом режиме Windows, который понижает и приоритет ввода-вывода.

## Формат данных внутри

```rust
enum SampleKind {
    Int { bits: u8 },
    Float32,
    Float64,
    Dsd { multiple: u16 },          // 64 для DSD64
}

struct StreamSpec {
    kind: SampleKind,
    sample_rate: u32,
    channels: ChannelLayout,
}
```

Блок данных хранится как перечисление по тем же видам. Благодаря этому поток DSD проходит конвейер, не превращаясь в PCM.

У конвейера два пути.

**Прямой путь.** Целочисленные семплы декодера доходят до устройства без перевода в числа с плавающей точкой. Допускается только дополнение нулями до более широкого контейнера: 16 бит в 24 или 32. Узлы обработки исключены из цепочки.

**Путь обработки.** Семплы переводятся в `f64`, проходят ресемплер, узлы DSP, громкость и дизеринг, затем квантуются в формат устройства.

Внутренний формат `f64` выбран из-за 32-битных исходников: `f32` хранит целые точно только до 24 бит.

## Декодеры

```rust
trait Decoder: Send {
    fn spec(&self) -> StreamSpec;
    fn frames(&self) -> Option<u64>;
    fn gapless(&self) -> GaplessInfo;            // задержка кодера и длина хвоста
    fn decode(&mut self, out: &mut Block) -> Result<Progress, DecodeError>;
    fn seek(&mut self, frame: u64) -> Result<u64, DecodeError>;
}
```

Основной декодер: Symphonia 0.6. Он написан на чистом Rust, не требует сторонних DLL и распространяется под MPL-2.0. Его покрытие неполное, поэтому нужны ещё два источника декодирования.

| Формат | Декодер | Gapless | Этап |
| --- | --- | --- | --- |
| MP3 | Symphonia | да, по заголовку LAME | MVP |
| FLAC | Symphonia | да | MVP |
| WAV, AIFF | Symphonia | да | MVP |
| ALAC | Symphonia | да | MVP |
| AAC-LC в M4A | Symphonia | в 0.6.1 задержка кодера в MP4 не обрезается, нужен свой разбор `iTunSMPB` | MVP, gapless после прототипа П2 |
| OGG Vorbis | Symphonia | да | MVP |
| Opus | libopus через адаптер к Symphonia | да, по pre-skip | 0.2 |
| HE-AAC, WMA, APE, WavPack, TAK, TTA, AC3, DTS | FFmpeg | зависит от формата | с пакетом FFmpeg |
| MKA | контейнер Matroska: Symphonia для FLAC, Vorbis, PCM и AAC внутри, FFmpeg для остальных кодеков | зависит от кодека | с пакетом FFmpeg |
| DSF, DFF | собственный разбор контейнера | да | 1.x |
| Образ с листом CUE | декодер исходного файла, границы треков из листа | да, поток не прерывается | 0.3, решение Р22 |

Поддержки Opus, HE-AAC и WavPack в выпущенной Symphonia нет, в её планах они значатся как неначатые. APE, WMA, AC3, DTS и DSD в планах отсутствуют. TAK и TTA она тоже не читает.

### Hi-Res

Разрядность 24 и 32 бита и частоты 96, 192 и 384 кГц проходят по прямому пути без изменений, если их принимает устройство. Опрос возможностей устройства идёт до 768 кГц. Когда устройство частоту не принимает, движок ресемплирует и показывает это в строке пути сигнала.

### Листы CUE

Трек из образа задаётся источником с диапазоном кадров внутри общего файла. Соседние треки одного образа играются одним непрерывным декодированием: граница трека остаётся только событием для интерфейса и статистики, звук на ней не трогается.

Позиции в листе записаны в кадрах компакт-диска, по 75 в секунде. Для 44,1 кГц это ровно 588 семплов на кадр, пересчёт точный.

Разбор листа живёт в сканере медиатеки. Там же решаются три частые проблемы: кодировка файла (Windows-1251, Shift-JIS и другие без пометки), лист на несколько файлов и предзазоры `INDEX 00`. Лист, встроенный в тег `CUESHEET` файла FLAC, читается так же.

### FFmpeg

FFmpeg закрывает редкие форматы одним решением. Условия его использования:

- сборка под LGPL, динамическая компоновка, DLL лежат рядом с программой;
- привязка через `ffmpeg-next` 9.x или `ffmpeg-the-third`;
- весь код, который касается FFmpeg, вынесен в отдельную библиотеку `vyra_ffmpeg.dll`. Основная программа загружает её через `libloading`, если файл есть.

Последний пункт делает FFmpeg необязательным пакетом. Готового крейта, который подключал бы FFmpeg во время работы, найти не удалось, поэтому граница проводится своей DLL. Поставлять ли пакет в основном установщике, записано в решении Р2.

Альтернатива для части форматов: системные декодеры Media Foundation. Они читают WMA и AAC без сторонних библиотек. APE, WavPack и DTS они не покрывают, так что FFmpeg всё равно понадобится.

Многоканальные AC3 и DTS декодируются в PCM. При стереоустройстве каналы сводятся узлом обработки. Передача сжатого потока на ресивер без декодирования отнесена к долгосрочным возможностям.

## Обработка

Узлы стоят в фиксированном порядке:

1. перевод в `f64`;
2. ресемплер, если частота источника не подходит устройству;
3. ReplayGain с защитой от клиппинга;
4. цепочка DSP: эквалайзер, позже плагины;
5. громкость с плавным изменением;
6. лимитер, включается при положительном усилении;
7. дизеринг TPDF и квантование.

```rust
trait DspNode: Send {
    fn prepare(&mut self, spec: StreamSpec, max_block: usize);
    fn process(&mut self, block: &mut FloatBlock);     // планарный f64, на месте
    fn latency_frames(&self) -> u32;
    fn tail_frames(&self) -> u32;
    fn reset(&mut self);
    fn set_param(&mut self, id: ParamId, value: f64);
    fn is_identity(&self) -> bool;                     // узел сейчас не меняет сигнал
}
```

Изменения параметров попадают в поток обработки через очередь без блокировок и сглаживаются за 20 мс, чтобы не было щелчков. Встроенный эквалайзер параметрический, на биквадратных фильтрах.

Ресемплер: `rubato` 5.x, синк-интерполяция с несколькими уровнями качества. За 2026 год у крейта вышли три мажорные версии со сменой API, поэтому он закрыт собственным трейтом, а версия зафиксирована. Альтернатива на случай проблем: `libsoxr` через FFI.

## Вывод

```rust
trait OutputBackend {
    fn devices(&self) -> Vec<DeviceInfo>;
    fn capabilities(&self, id: &DeviceId, mode: OutputMode) -> DeviceCaps;
    fn open(&self, id: &DeviceId, mode: OutputMode, spec: StreamSpec,
            source: RingConsumer) -> Result<Box<dyn OutputStream>, OutputError>;
    fn subscribe(&self, events: Sender<DeviceEvent>);
}
```

Реализаций три: `wasapi` для общего и монопольного режимов, `null` для тестов, позже `asio`.

### Почему WASAPI напрямую, без CPAL

CPAL был в исходном списке. Проверка версии 0.18.2 показала:

- режим вывода зашит как общий, запрос на монопольный режим открыт с 2016 года, работа над ним отложена до следующей мажорной версии;
- поток открывается с автоматическим преобразованием формата, что исключает bit-perfect;
- интерфейса для событий подключения и отключения устройств нет.

Главное достоинство CPAL, одна абстракция для всех систем, продукту только под Windows не нужно. Крейт `wasapi` версии 0.27 даёт общий и монопольный режимы, работу по событию, проверку поддерживаемых форматов и уведомления об устройствах. Он активно развивается, пять выпусков за 2026 год.

### Общий режим

Системный микшер принимает один формат: `float32` на частоте, выбранной в настройках устройства. Движок сам приводит звук к этому формату своим ресемплером. Bit-perfect в общем режиме невозможен по устройству Windows: после программы сигнал проходит через микшер.

### Монопольный режим

Устройство открывается в формате трека. При первом обращении движок опрашивает устройство по сетке частот от 44,1 до 768 кГц и разрядностей 16, 24, 24 в контейнере 32 и 32 бита. Результат кешируется по идентификатору устройства и версии драйвера.

Монопольный доступ берётся при старте воспроизведения. Он освобождается при остановке и после паузы длиннее 10 секунд, чтобы звук могли получить другие программы. Интервал настраивается.

Если устройство занято, движок сообщает об ошибке и предлагает повторить или перейти в общий режим. Молчаливого перехода нет: пользователь, который включил монопольный режим ради качества, должен знать, что его лишился. Автоматический переход можно разрешить в настройках.

## Устройства

Движок подписан на события Windows о появлении, исчезновении и смене устройства по умолчанию.

В настройках профиля цель вывода задаётся одним из двух способов: следовать за системным устройством по умолчанию или держаться конкретного устройства.

Переключение идёт так:

1. на пути обработки звук затухает за 30 мс;
2. поток вывода останавливается, запоминается номер кадра, который реально прозвучал, с поправкой на задержку буферов;
3. открывается новое устройство, заново согласуется формат; путь может смениться с прямого на путь обработки или обратно;
4. цепочка обработки перестраивается под новый формат;
5. декодер перематывается на запомненный кадр, буферы заполняются, вывод стартует.

Цель по времени: до 300 мс между командой и звуком.

Когда закреплённое устройство пропало (например, отключён USB-ЦАП), воспроизведение встаёт на паузу с сохранением позиции. Автоматический переход на устройство по умолчанию выключен: музыка, внезапно заигравшая из динамиков ноутбука, хуже паузы. Поведение настраивается.

Смена частоты между треками в монопольном режиме требует открыть поток заново. Это пауза в 100–500 мс. Некоторым ЦАП после смены частоты нужно время на переключение реле, для них есть настраиваемая задержка. Тем, кому непрерывность важнее точности, подойдёт настройка фиксированной частоты вывода.

## Gapless

Движок держит два источника: текущий и следующий. Примерно за 10 секунд до конца трека он шлёт событие `NeedNext`, слой воспроизведения отвечает следующим источником из очереди. Декодер следующего трека открывается заранее, заодно проверяется, что файл читается.

Если формат следующего трека совпадает с текущим, его кадры дописываются в тот же поток. Задержка кодера и хвост обрезаются по `GaplessInfo`, стык получается точным до семпла.

Если формат другой, на пути обработки ресемплер перестраивается и поток не прерывается. На прямом пути поток вывода открывается заново, короткая пауза неизбежна.

Цепочка DSP на границе треков не сбрасывается, хвосты фильтров доигрывают.

Событие начала трека отправляется в момент, когда его первый кадр доходит до устройства, с поправкой на задержку. Интерфейс меняет обложку тогда же, когда меняется звук, а статистика получает точное время.

## Bit-perfect

Определение: байты, переданные в API устройства, равны семплам из декодера. Разрешено только дополнение нулями до более широкого контейнера.

Признак выставляется, когда выполнены все условия:

- источник без потерь или PCM;
- вывод монопольный;
- устройство принимает частоту, раскладку каналов и разрядность источника;
- каждый узел обработки сообщает `is_identity`: эквалайзер выключен, ReplayGain выключен, ресемплинга нет, громкость 100%.

Для MP3 и других форматов с потерями термин не применяется. Интерфейс пишет для них «Без обработки».

Признак считает движок, интерфейс его только показывает:

```rust
struct SignalPath {
    source: StreamSpec,
    codec: Codec,
    lossless: bool,
    stages: Vec<Stage>,                 // Resample, ReplayGain, Eq, Volume, Dither, ChannelMix
    output: StreamSpec,
    device: DeviceId,
    mode: OutputMode,
    bit_perfect: bool,
    reasons: Vec<NotBitPerfect>,        // что именно мешает
}
```

Список `reasons` нужен интерфейсу, чтобы объяснить: «Не bit-perfect: включён ReplayGain, устройство не принимает 96 кГц».

Громкость на прямом пути закреплена на 100%. Если у устройства есть аппаратный регулятор, ползунок управляет им через `IAudioEndpointVolume`, цифровой сигнал при этом не меняется. Если регулятора нет, ползунок неактивен и рядом написано почему.

Режим «Только bit-perfect» включается одним переключателем. Движок отключает всё, что меняет сигнал, и отказывается играть трек, который устройство не принимает в исходном формате, вместо молчаливого ресемплинга.

## ReplayGain

Движок читает теги `REPLAYGAIN_*` и `R128_*`. Режим альбома или трека приходит из контекста воспроизведения. Для файлов без тегов действует отдельное предусиление. Защита от клиппинга использует пиковое значение из тегов.

Анализ громкости по EBU R128 (крейт `ebur128`) запускается фоновой задачей. Результаты ложатся в базу. В теги они записываются только отдельной командой пользователя, как требует ручной режим метаданных.

## DSD и ASIO

Реализация отложена, но конструкция учитывает оба пункта уже сейчас.

`StreamSpec` и блоки данных умеют нести поток DSD. Вывод DSD возможен тремя способами: DoP поверх монопольного WASAPI, родной DSD через ASIO, преобразование в PCM для обычных ЦАП. DoP кодирует DSD внутри 24-битного PCM с маркерами, любая обработка их разрушает, поэтому для DoP движок принудительно выбирает прямой путь.

ASIO ложится в трейт `OutputBackend` без изменений конвейера. С октября 2025 года ASIO SDK распространяется на выбор под GPLv3 или по соглашению со Steinberg. VYRA выпускается под GPL-3.0 (решение Р2), поэтому SDK используется без соглашения.

Драйвер ASIO представляет собой сторонний код внутри процесса плеера, и его сбой роняет всю программу. API движка построен на сообщениях, поэтому вывод при необходимости можно вынести в отдельный процесс без переделки остального.

## API движка

Команды: `Load`, `SetNext`, `ClearNext`, `Play`, `Pause`, `Stop`, `Seek`, `SetVolume`, `SetOutput`, `SetDspChain`, `SetParam`, `SetReplayGain`, `QueryDevices`.

События: `StateChanged`, `TrackStarted`, `TrackEnded`, `NeedNext`, `Position`, `SignalPathChanged`, `DeviceEvent`, `Underrun`, `Error`.

## Устойчивость

**Ошибка декодирования.** Повреждённый пакет пропускается с коротким затуханием, случай пишется в лог. После нескольких ошибок подряд трек завершается с причиной, очередь идёт дальше.

**Медленное чтение.** Сетевая папка или уснувший диск опустошают буфер. Движок переходит в состояние `Buffering`, выводит тишину и продолжает, когда данные появятся.

**Занятые файлы.** Файлы открываются с разрешением на чтение, запись и удаление другими процессами. Файловый менеджер может переименовать и переместить играющий файл. Запись тегов в играющий файл откладывается до конца трека.

**Сторож.** Управляющий поток следит за отметками потока вывода. Если их нет дольше двух секунд, поток открывается заново.

## Проверка

Тестовый бэкенд `null` записывает всё, что получил бы драйвер. На нём построены автоматические тесты:

- хеш вывода на прямом пути равен хешу эталонного декодирования того же файла;
- склейка двух половин одного трека совпадает с целым треком до семпла, для каждого формата с поддержкой gapless;
- перемотка в произвольную точку даёт те же семплы, что и последовательное декодирование.

Работа с настоящими устройствами проверяется вручную по списку из [roadmap.md](roadmap.md): два разных ЦАП, встроенный кодек, Bluetooth, отключение устройства во время игры.
